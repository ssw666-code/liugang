## 正文（约 200 字）

本次拆解 `brainstorming` 技能包。其 **触发描述（description）** 写明：在任何创造性工作（做功能、改行为、做计划等）之前必须先用——因此 AI 会在「动手写代码前」优先加载它，而不是一上来实现。**工作步骤**在 `SKILL.md` 正文里按纪律展开：先澄清真实意图 → 一次只问一个会改变设计的问题 → 摆出可选方案让人选定 → 写设计文档并获批准 → 再调用 `writing-plans`；红队式「禁止菜单式诱导、未批准不编码」写进 Red Flags。细节不堆在正文：`visual-companion.md`、`builder-check-prompt.md` 按需加载；`scripts/`（如 `server.cjs`、起停脚本）支撑可视化伴生能力。三要素分工清晰：**触发决定何时用，步骤决定怎么问，配套文件控制上下文成本**——这正是第 3 周用 Superpowers 重做项目时要遵守的流程边界。

## 结构对照（备查，答辩可讲）

| 要素 | 本技能中的具体内容 | 作用 |
|------|--------------------|------|
| 触发描述 | frontmatter `description`：创造性工作前必须使用 | 决定 AI「何时加载」；写得宽则易触发，写得窄则易漏触发 |
| 工作步骤 | 澄清 → 方案对比 → 设计文档 → 批准 → writing-plans | 把资深工程师的「先想清楚再动手」固化成可执行流程 |
| 配套引用 | `visual-companion.md`、`builder-check-prompt.md` | 渐进披露：长说明不占常驻上下文 |
| 配套脚本 | `scripts/` 目录 | 可执行检查/辅助，与纯文字清单分离 |

---

## 与本项目的衔接（一句话）

第 1 周我们用「结构化提问 + proposal」人工完成了 brainstorming 同类工作；第 3 周起应改由该技能驱动澄清与设计门禁，**不再混用第 1–2 周的纯 SDD 口头流程**，但可继承已确认的范围结论（F/X/A）作为文字经验，而非复制代码。
