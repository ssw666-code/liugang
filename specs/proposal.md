## 1. 背景与目标

### 1.1 背景

软件工程团队的日常工作痕迹分散在 GitHub 提交与 Pull Request、飞书任务流转、飞书群消息等多个平台。成员撰写日报时往往依赖记忆回忆当日工作，容易遗漏真实产出；协作成果（共同改接口、共同修缺陷）归属不清；每人格式不一，团队负责人还需手工汇总成团队日报。

课程仿真企业背景要求建设「智能日报生成器」：从成员真实工作数据中生成个人与团队日报，形成采集 → 生成 → 确认 → 推送 → 历史留存的闭环。本项目定位为跨源日报编排工具，**不是**完整项目管理平台。

### 1.2 目标

构建一个本地可运行的 Web 工具，在统一工作日时间窗内采集 GitHub 与飞书相关工作数据（飞书任务可用 Mock），半自动生成可编辑的个人日报草稿，经成员提交与负责人确认后形成正式日报，并通过邮件主路径完成通知与分发，使用 SQLite 保存历史与版本，满足课程演示与验收。

**可度量目标（课程交付口径）：**

1. 支持至少 3 类数据源参与生成链路：GitHub Commits+PRs、飞书群消息、飞书任务（Mock 可验收）。
2. 个人日报须经「草稿 → 编辑 → 提交」后生效；团队日报须经负责人确认后生效。
3. 邮件推送覆盖：个人提交成功、逾期提醒、团队确认后群发、采集失败告警（可真实发送或按在线演示路径验证）。
4. 提供离线 Mock 全流程演示路径，答辩不依赖外网亦可跑通主闭环。

### 1.3 目标用户

| 角色 | 类型 | 说明 |
|------|------|------|
| 普通开发成员 | 主要使用者（数据生产者） | 生成、编辑、提交个人日报；查看本人历史与素材 |
| 团队负责人 / 项目经理 | 主要读者与确认者（数据消费者） | 手动汇总团队日报、确认后分发；查看全员 |
| 系统管理员 | 规则决策者 | 配置下班时间、过滤规则、截止延迟、凭证；演示重置 |

- 推送接收方均落在系统用户角色内，不存在「只收日报、不登录」的旁听用户。  
- 一人可兼多角色，须支持当前身份切换；权限以**当前激活角色**为准。

## 2. 功能范围

### 2.1 做什么（本期）

> 下列条目逐条编号，供后续用例与 tasks 追溯。

#### 数据采集

- **F-01** 对接 GitHub，采集统计区间内的 **Commits** 与 **Pull Requests**（必做；可切换 Mock）。
- **F-02** 采集飞书群消息中的有效工作信息（必做；可切换 Mock）：先全量纳入，再按规则/黑名单过滤表情包、签到、闲聊；成员仍可增删。
- **F-03** 飞书任务流转纳入正式需求，本期可用 **Mock 数据**演示（全部数据源均需可切换 Mock/样例模式）。
- **F-04** 采集触发方式：用户点击生成日报时**实时拉取**；三源同一触发方式。**不是**后台持续监听外部事件。
- **F-05** 统计时区统一 **Asia/Shanghai**；统计区间为「前一天下班时刻 → 当天下班时刻」；下班时刻管理员可配，默认 **18:00**；周末/节假日仍按同一下班时刻切分。
- **F-06** 归属规则：Commit 按 author/committer；PR 创建者与 reviewer 均可出现并标注角色；飞书任务按执行人/负责人；群消息按发送者，被 @ 者可纳入并标「相关」；允许认领未归属条目并标「手动认领」；团队冲突合并为一条并列出参与者。
- **F-07** 默认排除 Bot/CI 等非人工账号提交（如 `dependabot`、`github-actions[bot]`），管理员可维护排除名单。

#### 日报生成与管理

- **F-08** 个人日报：多源采集 → 系统生成半自动草稿 → 成员编辑 → **提交后正式生效**。
- **F-09** 个人日报章节固定为三章：**今日完成 / 进行中 / 问题与风险**（不要「明日计划」）。
- **F-10** 异常：无数据时预填提示文案，可改后提交；支持请假/缺勤状态 + 一键短日报；单源失败时其他源照常，失败源标「采集失败」，仍出草稿。
- **F-11** 团队日报：负责人或管理员**手动触发**；按「完成 / 进行中 / 风险」主题合并；可增删改成员条目；**负责人确认后**正式生效。
- **F-12** 未提交成员：列出姓名并标「未提交」，不进入主题正文；负责人修改**不回写**个人正式日报。
- **F-13** 历史日报：按日期查询个人/团队历史、关键词搜索、按成员筛选；成员仅看自己，负责人/管理员看全员；**不做导出**。
- **F-14** 已提交/已确认后仍可编辑，并保留版本历史（个人与团队分链；每版含版本号、编辑者、时间、完整正文快照）。
- **F-15** 生成时固化统计区间快照（`workday_date`、`range_start`、`range_end`、`off_work_time_used`）；管理员事后修改下班时间**不重算**历史日报。
- **F-16** 工作日主展示日期 = 区间结束日的日历日期；详情须同时展示完整 `[range_start, range_end]`。

#### 推送通知

- **F-17** **邮件推送为必做**，尽量真实发送：个人提交成功通知、逾期提醒、团队日报确认后邮件群发、采集失败告警（管理员）。
- **F-18** 团队日报确认后**立即**推送；主路径为邮件群发。
- **F-19** 逾期：管理员可配截止时间；默认相对下班固定延迟（默认下班 18:00 时截止为 **18:30**）；系统到点自动提醒，同人同日去重；服务需常驻（默认进程内分钟级扫描，可补扫）。
- **F-20** 每一次推送尝试写入 `notification_log`（业务类型、关联日报、渠道、接收方、时间、成功/失败、失败原因）；团队确认页展示最近一次推送状态。
- **F-21** 飞书群机器人推送为**可选加分**，不是必做验收项。

#### 用户、权限与演示

- **F-22** 本地账号登录；三角色（成员 / 负责人·PM / 管理员）；一人可兼多角色；支持身份/工作台切换。
- **F-23** 第三方登录**仅预留接口，不完整实现**。
- **F-24** 敏感凭证由管理员配置，**加密存入 SQLite**；加密主密钥来自环境变量 `REPORT_SECRET_KEY`；真实 Token **不得**提交到 Git。
- **F-25** 原始采集素材：负责人/管理员可见全员；普通成员仅自己。
- **F-26** 管理员可维护：下班时间、群消息过滤规则、截止延迟分钟数、Bot 排除名单等；过滤规则变更不影响已生成草稿正文。
- **F-27** 管理员支持一键清空演示业务数据 / 重置库：执行前二次确认；仅清业务数据，保留账号角色与系统配置（含凭证密文）；正常运行期不自动清理历史。
- **F-28** 提供 README「离线 Mock 全流程演示路径」与「在线邮件演示路径」两套说明。

### 2.2 不做什么（本期明确排除）

| 编号 | 排除项 | 理由 |
|------|--------|------|
| X-01 | 不做完整项目管理 / 看板 / 缺陷跟踪平台 | 项目定位是日报编排工具；膨胀会偏离课程闭环 |
| X-02 | 不做日报导出（Excel/PDF 等） | 需求澄清明确不做导出 |
| X-03 | 不做第三方登录的完整实现 | 课程内只做本地账号；第三方仅预留 |
| X-04 | 不把飞书机器人 / 飞书个人消息当作必做 | 邮件为主路径；飞书为可选加分，避免双通道绑死验收 |
| X-05 | 不做后台持续实时监听 / 长连接事件订阅作为采集主路径 | 已确认采集为「生成时拉取」；与逾期扫描分离 |
| X-06 | 不做强制外部大模型智能摘要 | 本期以规则过滤与归类生成可编辑草稿；是否引入 LLM 另议 |
| X-07 | 不做考勤数据采集 | 属课程第 4 周变更涟漪（v1.1）场景，非本期初始范围 |
| X-08 | 不做按日期重算并覆盖历史日报 | 历史区间快照固化，保证可追溯 |
| X-09 | 不做多租户 / 多团队隔离的生产级架构 | 本地单机演示即可，避免过度设计 |

### 2.3 技术约束

| 约束项 | 内容 | 状态 |
|--------|------|------|
| 应用形态 | Web 应用（浏览器访问） | 已确认 |
| 部署 | 本地单机部署即可 | 已确认 |
| 数据存储 | 本地 **SQLite**（存历史日报、版本、配置、推送日志等） | 已确认 |

## 3. 验收标准

> 每条应可转化为测试或演示核对。性能数字为**课程演示建议指标**（澄清未设硬性性能 KPI；指导书与教材要求性能验收须含可量化数值）。

### 3.1 功能验收

- [ ] **A-01** 三角色本地账号可登录；兼多角色用户可切换身份，且敏感操作按当前激活角色鉴权。
- [ ] **A-02** 生成个人日报时可获取指定统计区间内 GitHub Commits 与 PRs（真实或 Mock）；Bot/CI 默认不进入自动归类素材。
- [ ] **A-03** 生成时可获取飞书群消息素材，噪声消息被过滤，成员仍可增删改。
- [ ] **A-04** 飞书任务可通过 Mock 进入生成链路，并按执行人/负责人归属；文档不宣称「已完成真实任务 API 接入」。
- [ ] **A-05** 个人日报草稿包含且仅包含「今日完成 / 进行中 / 问题与风险」三章；提交前为草稿，提交后正式生效。
- [ ] **A-06** 无数据日可生成带提示文案的草稿并提交；请假短报可用；单源失败时草稿仍生成且失败源有「采集失败」标注。
- [ ] **A-07** 负责人可手动生成团队日报；未提交成员仅名单标注；确认后生效；对团队稿的修改不回写个人正式日报。
- [ ] **A-08** 团队日报确认后触发邮件群发；个人提交成功、逾期、采集失败告警均可在邮件或 `notification_log` 中核验。
- [ ] **A-09** `notification_log` 可查询推送结果；团队确认页展示最近一次推送状态。
- [ ] **A-10** 可按日期 / 成员 / 关键词查询历史；再编辑产生新版本；可浏览历史版本只读快照。
- [ ] **A-11** 修改全局下班时间后，已生成日报的区间快照不变；新生成日报使用新配置。
- [ ] **A-12** 仓库中无真实 Token；无 `REPORT_SECRET_KEY` 时拒绝读写凭证并提示管理员。
- [ ] **A-13** 一键重置仅清空业务数据并需二次确认；账号与配置保留。
- [ ] **A-14** 按 README 离线 Mock 路径可完成：采集 → 草稿 → 提交 → 团队确认 → 历史查询（推送可用 Mock/日志模拟）。

### 3.2 性能验收

- [ ] **P-01** 在演示规模（建议 ≤10 名成员样例数据）下，单次「点击生成个人日报」（含三源拉取或 Mock）端到端耗时 **&lt; 60s**。
- [ ] **P-02** 单一数据源超时或失败时，**不阻断**其他数据源采集与草稿生成。
- [ ] **P-03** 逾期扫描默认 **分钟级**触发检查；应用重启后能补扫仍未提醒的逾期项。
- [ ] **P-04** 采集失败的数据源必须在草稿/界面中**显式标注**，严禁静默跳过。

### 3.3 边界场景

- [ ] **B-01** 成员当日无 Commit、无任务、无有效群消息时，对应章节显示约定提示（如「今日无代码/任务记录」类文案），仍允许编辑后提交。
- [ ] **B-02** GitHub API 限流或失败时：标记该源失败并仍出草稿；Mock 模式可完整演示。
- [ ] **B-03** 飞书凭证不可用或无外网时：可切换 Mock，离线路径仍可演示主闭环。
- [ ] **B-04** 到达截止时刻仍有未提交成员：自动发送逾期提醒，且同一成员同一工作日不重复成功提醒。
- [ ] **B-05** 周末/节假日：仍按配置的下班时刻切分区间（不因节假日自动跳过生成；与教材示例「自动跳过」不同，以本组确认为准）。
- [ ] **B-06** 邮件发送失败时：`notification_log` 记录失败原因；团队确认页可看到失败状态。

## 4. 术语定义

| 术语 | 定义 |
|------|------|
| 个人日报 | 面向单个成员的三章日报；成员提交后正式生效 |
| 团队日报 | 由负责人/管理员手动汇总并确认后生效的主题合并日报 |
| 成员 | 系统中的普通开发角色用户；可与 GitHub / 飞书身份映射 |
| 负责人 / PM | 可触发并确认团队日报、查看全员数据的角色 |
| 管理员 | 可配置系统规则、凭证与演示重置的角色 |
| 数据源 | 提供原始工作数据的来源：GitHub、飞书群消息、飞书任务（可 Mock） |
| 采集窗口 / 统计区间 | 单次生成覆盖的时间跨度：前一天下班时刻 → 当天下班时刻（Asia/Shanghai） |
| 工作日（workday_date） | 统计区间结束日的日历日期，用于列表、筛选与邮件标题 |
| 半自动草稿 | 系统根据素材自动归类生成、须经成员编辑提交才生效的日报初稿 |
| Mock | 样例/模拟数据模式，用于无真实权限或无外网时的演示 |
| notification_log | 推送尝试的持久化记录表/集合 |
