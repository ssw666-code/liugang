# 规范目录约定

`specs/` 是需求、设计与任务的事实来源。代码行为与规范不一致时，必须先确认以哪一方为准，再同步修改另一方并留下提交记录。

## 文件职责

| 文件 | 当前状态 | 说明 |
| --- | --- | --- |
| `proposal.md` | 第一周草案 v0.1 | 目标、范围、排除项、技术约束和可度量成功标准 |
| `design.md` | 第二周创建 | 架构、模块职责、数据模型、接口契约、ADR 与非功能约束 |
| `tasks.md` | 第二周创建 | 带依赖、交付物和验收标准的实现任务 |
| `decisions/` | 第二周创建 | 单独归档 ADR；小型决策可先写入 `design.md` |

## 变更流程

1. 需求变化先修改 `proposal.md`，记录版本与变更原因。
2. 设计影响分析写入 `design.md` 或新的 ADR。
3. 可执行变更拆入 `tasks.md`，每条任务必须有验收标准。
4. 代码提交引用相关规范编号，例如 `feat(collector): implement R-01`。
5. 提交前检查代码、测试与 `specs/` 是否一致。

## 分支与提交

- `main`：保持可运行的最小版本。
- `feature/<short-name>`：新增功能。
- `fix/<short-name>`：缺陷修复。
- `docs/<short-name>`：仅文档变更。
- 提交格式：`type(scope): summary`。
- 每次提交只处理一个可验证的小目标。

## 安全边界

- 仓库只保存 `.env.example`，不保存真实令牌、授权码、Cookie 或个人信息。
- 环境验证和日志只记录凭证是否可用，不记录凭证值。
- 示例数据必须脱敏，外部 API 响应不得原样提交。
